# BE-150 — Kompensasi objek chunk ketika pencatatan database gagal

**Phase:** 6 · **Parent resmi:** T40, T41, T46 · **Jenis:** BUG FIX
**Status implementasi:** IMPLEMENTED 2026-09-30 (menunggu human review dan security review) · **Hasil pengujian:** PASS lokal (RED `aea5adc` → GREEN `4345623`; Pest penuh dengan MySQL 8.4; [handoff](../handoff/2026-09-30-fix-miss-feature.md))

## Tujuan dan sumber

Pastikan objek chunk sementara yang berhasil ditulis ke private storage tetapi gagal dicatat di database tidak tertinggal tanpa referensi dan tidak pernah diakui sebagai progress upload. Ini melengkapi jalur race yang sudah menghapus objek saat `addChunk` mengembalikan `null`; pengecualian transaksi masih melewati kompensasi tersebut.

Sumber: [11A](../project_doc/11A_Resumable_Attachment_Upload_Synchronization.md) §12–14, §21–22; [12](../project_doc/12_API_Contract.md) §55; [15](../project_doc/15_Coding_Rules_AGENTS.md) §34, §46; [16](../project_doc/16_Testing_Specification.md) §33–34, §50–53; [19](../project_doc/19_Task_Implementation_Plan.md) T40, T41, T46.

## Prasyarat dan kondisi sekarang

[BE-094](BE-094.md), [BE-095](BE-095.md), [BE-102](BE-102.md). Pada `AttachmentUploadService::acceptChunk`, storage write terjadi sebelum transaksi metadata; kompensasi saat ini hanya berjalan bila transaksi selesai dengan hasil `false`. Ini adalah temuan kode saat perencanaan, bukan bukti test RED/GREEN.

## File dan batas antarmuka

- Implementasi yang diperiksa: `app/Services/Attachment/AttachmentUploadService.php`; gunakan kontrak private storage dan repository yang sudah ada.
- Test pertama: `tests/Feature/Attachment/AttachmentUploadTest.php` atau focused MySQL integration test yang membuktikan kegagalan setelah write.
- Tidak menambah route, status, kolom, dependency, atau mengubah chunk geometry/24h expiry. Jangan menghapus chunk yang telah diterima request lain dalam race.

## Acceptance criteria

1. **AC-01:** Setelah write private chunk berhasil lalu operasi database melempar exception, chunk baru yang tidak direferensikan metadata dibersihkan atau tercatat dalam mekanisme cleanup yang benar-benar dapat menemukannya; tidak ada accepted chunk/expiry baru yang diklaim.
2. **AC-02:** Kegagalan kompensasi sendiri tetap terlihat dalam diagnosis aman: Technical Log berisi `upload_id`, `chunk_index`, dan kelas exception, tanpa storage key. Response tidak menjadi sukses palsu dan tidak membuka storage key ke klien. **Keputusan pemilik 2026-09-30 ([G23](06_GAP_DAN_KEPUTUSAN.md#g23)):** tidak ada mekanisme sweep baru; objek yang tersisa pada kegagalan ganda adalah batas yang diketahui.
3. **AC-03:** Duplicate byte-identical dan race same-index tetap idempoten; objek yang sudah authoritative milik request pemenang tidak terhapus.
